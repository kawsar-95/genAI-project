### Contract / side-channel risks
- **Money-moving controller check:**
  - `sendMoney` still uses `sequelize.transaction` + READ_COMMITTED + `SELECT … FOR UPDATE` + `replacements` (`:98-107`).
  - The three ledger rows are unchanged: debit `amt + fee`, credit `amt`, SYSTEM credit `fee`.
- **The limit check now runs inside the lock.**
  - It follows the balance check (`:107` → `:125`). BRD §7.3 precondition 7 and §8.3 say limits are checked *first*.
  - A customer who is over the limit **and** short of balance now gets 208 "Insufficient balance" instead of the 400 limit error. *(SM-H02 requirement, Gaps)*
- **The critical section is longer.**
  - The locked transaction now also reads `TransactionLimits` and runs two aggregate scans on `Transactions`, which has no `account` index (PK only).
  - All money-moving transactions wait on each other across the whole table, so lock-wait timeouts may surface as generic 500s.
- **Shared limit across types:**
  - Payment (`:72`) and Withdraw (`:66`) still check the limit outside their lock.
  - The shared Customer limit (BRD §8.2) can still be broken by a mix of parallel SendMoney, Payment and Withdraw requests. *(SM-H02 AC-7 is not met)*
- **API contract drift:**
  - `swagger/swaggerTrnx.yaml:438-470` documents only 201, 208 and 404 for sendmoney, so the new 400s are undocumented:
    - `from_account is required and must be a string`
    - `to_account is required and must be a string`
    - `Amount must be a valid number greater than 0 with at most 2 decimal places`
    - `LIMIT_EXCEEDED` → 400 with `details`
  - The 500 response is undocumented too.
  - Swagger says same-account returns 208, but the code returns 400. This drift predates the PR.
  - `endpoints.md:300-310` has no error examples.
- **Stricter input format:**
  - `"20."`, `".5"` and `"1e1"` used to be accepted as amounts and are now rejected. Plain numeric strings (`"20"`) and JSON numbers still work.
  - The Postman collection (`web/api_doc/…postman_collection.json:409`) sends `"amount": 20`, which is unaffected.
- **Error message change:**
  - Every invalid-amount case gets the new longer message, except `0` and `"0"`, which keep the old one (`:48`).
  - The SM-L01 requirement expects exactly `Amount must be a valid number greater than 0`. *(SM-L01 AC-1 to AC-3)*
- **Account normalization only trims spaces:**
  - A zero-width space or a full-width digit still reaches the `utf8mb4_unicode_ci` lookup and gets past the `===` same-account check (`:75`).
  - *(SM-M01 AC-3 is not met; confirmed with a read-only query on 2026-10-07)*
- **Overlap with qa-findings:**
  - The PR touches `08-send-money-bugs.md` SM-H01 to SM-L03 (intended).
  - It also overlaps `transaction-limits.report.md` G-1 (the same race).
  - CASHIN-H01 and CASHIN-M04 (the same crash and leak patterns in deposit, payment, withdraw and adminDeposit) are **not** touched.

### Unresolved
- **Lock behaviour under load** (lock-wait timeouts, throughput) can't be proved statically. It depends on the table size and the missing `account` index.
- **Sequelize CLS** is not enabled (no `useCLS` or `cls-hooked` in the API). So `transaction: undefined` in the Payment and Withdraw paths was confirmed to behave the same as before. If CLS is ever enabled, re-check this.
- **Other receipt pages** (agent cash-in, agent payment, customer cash-out, customer payment) have the same "Total Amount" wording. They aren't changed, so they aren't in the impact chain, but they're relevant to the SM-L02 requirement question.
