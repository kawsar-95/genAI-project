# AI Agent Testing & Test Automation Framework Implementation
## A Comprehensive Blueprint: From Local Sub-Agent Architecture to Production-Grade Agentic QA (2026)

---

## Executive Summary

As software development transitions from static code to **autonomous AI agents**, traditional deterministic QA automation (e.g., hardcoded Selenium or static unit tests) faces a fundamental wall. AI agents introduce multi-step reasoning, dynamic tool selection, non-deterministic decision pathways, and state accumulation.

This document presents the **complete end-to-end framework** for testing AI agents and implementing agentic test automation. It synthesizes practical architecture—sub-agents, skills, adversarial verification, and prompt chaining—with 2026 industry standards for trajectory auditing and structural evaluation.

## 2. Core Differences: Main Agent vs. Sub-Agents vs. Skills

| Dimension | Main Agent (Orchestrator) | Sub-Agent (Specialized Persona) | Skill (`SKILL.md`) |
| :--- | :--- | :--- | :--- |
| **Role** | General reasoning, task decomposition, user interaction | Bounded executor with restricted tools, specialized prompt, and target model | Step-by-step instructions and guidelines defining *how* a task is executed |
| **Tool Scope** | Unrestricted access to all available workspace/system tools | Restricted subset (e.g., CLI browser + `curl` only; read-only access for reviewers) | Specifies recommended tools, but execution depends on agent binding |
| **Token Cost** | Higher token consumption due to broad context and unrestricted search | Highly token-efficient; operates within strict boundaries without spawning extra tools | Minimal; loaded into context as explicit procedural memory |
| **Model Selection**| Balanced model (e.g., Claude Sonnet) | Tailored (e.g., Sonnet for speed/execution, Opus 5.5 for deep thinking) | Model-agnostic markdown definition |

## 3. End-to-End Agentic STLC Workflow

The Software Testing Life Cycle (STLC) for AI agent systems is structured into explicit, linked phases to eliminate hallucination and maintain complete traceability:

```
[Requirement Analysis] ➔ [Blast Radius Identification] ➔ [Test Charter Creation] 
       ➔ [Test Case Preparation (test.md)] ➔ [Test Executor Sub-Agent (test-result.md)] 
       ➔ [Ad-hoc Bug Hunting (FindBug Skill)] ➔ [Adversarial Verification] ➔ [Defect Reporting (bug.md)]
```

### Phase 1: Requirement Analysis & Blast Radius
- **Input**: Software Requirement Specification (SRS), PRD, or feature request.
- **Process**: Trace architectural dependencies across modules. Identify impacted microservices, database schemas, and API endpoints (the "blast radius").
- **Output**: Structured dependency map ensuring no high-risk side effects are missed.

### Phase 2: Test Charter & Test Case Design (`test.md`)
- **Process**: Convert requirement insights into structured Test Charters, then generate detailed test cases in standard Markdown format.
- **Tagging & Metadata**: Each test case includes TC ID, Title, Priority (`High`, `Mid`, `Low`), Category (`Smoke`, `Sanity`, `Regression`, `Security`, `API`, `UI`), Steps, and Expected Outcome.

### Phase 3: Deterministic Test Execution (`test-result.md`)
- **Executor**: `test-executor-agent` bound to the `test-execute` skill.
- **Constraint**: **Do NOT hunt for new bugs during execution.** The executor must follow pre-scripted steps blindly to prevent context drift and performance bottlenecks.
- **Tools**:
  - `agent-browser`: Lightweight CLI/console browser automation for speed and low token overhead.
  - `curl`: API validation.
- **Output**: Standardized report saved to `artifacts/[module].test-result.md` containing:
  - TC ID, Test Title, Test Data, Expected Result (Clean Natural Language), Actual Result, and Status (`PASS` / `FAIL` / `NOT EXECUTED`).

### Phase 4: Exploratory & Ad-Hoc Bug Hunting (`findbug` Skill)
- **Trigger**: Executed *after* scripted test cases are validated.
- **Process**: Inspects PR changes, git diffs, and core code logic. Searches for edge cases, race conditions, memory leaks, or unhandled exceptions missing from static test cases.

### Phase 5: Adversarial Review & Defect Gate (`qa-reviewer-agent`)
- **Reviewer**: `qa-reviewer-agent` (Adversarial Sub-Agent running on Opus 5.5 / 3.5).
- **Rule**: **Read-Only Access.** Cannot edit code or create reports directly.
- **Behavior**:
  - Applies a default stance of **falsification** ("Assume every reported bug is a false positive until proven otherwise").
  - Validates business logic via code intelligence tools (`graphify`, `serena`).
  - Requires explicit trace/code evidence (graph node, code symbol, log entry).
  - Flags invalid bugs or re-prioritizes severity (e.g., downgrading from `High` to `Mid`).
- **Enforcement**: Configured via `pre-tool` hooks in `settings.json` to inspect draft defects before `bug.md` is committed to the workspace.

## 4. Practical Implementation Techniques

### A. Few-Shot Prompting for Clean Formatting
When generating execution reports, instruct LLMs using concrete input/output examples rather than loose descriptions.
- *Bad Prompt*: "Write expected and actual results in clean language."
- *Few-Shot Example*:
  ```
  Expected Result: The agent balance should increase by the full deposit amount with zero commission deducted.
  Actual Result: As expected.
  ```

### B. Prompt Chaining & Compound Engineering
1. **Instruction**: Generate report -> 2. **Evaluation**: User/system critiques formatting -> 3. **Polish**: LLM refines output style -> 4. **Skill Update**: Feed refined pattern back into `SKILL.md` for permanent agent memory.

### C. Hook-Based Governance (`settings.json`)
Use automated hooks to enforce mandatory gates:
```json
{
  "hooks": {
    "pre-tool": {
      "command": "spawn-qa-reviewer-agent --target-artifact bug.md",
      "description": "Trigger adversarial QA review before saving defect reports"
    }
  }
}
```

## 5. Tooling Strategy: CLI Fast-Path vs. Deep Browser Automation

| Automation Layer | Tool / Mechanism | Best Use Case | Performance & Token Profile |
| :--- | :--- | :--- | :--- |
| **Lightweight UI Testing** | `agent-browser` (CLI Console) | Bulk test case execution, form fills, standard UI navigation | **Extremely Fast & Token Efficient** (runs in console without heavy DOM context dumping) |
| **Deep Visual & Network QA**| `playwright-mcp` | Complex DOM inspection, network traffic analysis, race condition debugging | **High Token Overhead** (requires accessibility tree snapshotting) |
| **Skill-Based Automation** | `playwright-cli` Skills | Generating re-usable end-to-end Playwright code from natural language | **Balanced** (generates deterministic Playwright `.spec.ts` files) |
| **Backend API QA** | `curl` / HTTP MCP | REST/GraphQL endpoint verification, payload assertion | **Ultra Light & Deterministic** |
| **Performance Testing** | `k6` CLI Scripts | Load testing, concurrency bottlenecks, API response degradation | Executed via CLI; script generation and metric analysis handled by LLM |

## 6. 2026 Industry Standards for Agent Evaluation

Modern AI agent QA spans two distinct evaluation layers:

1. **Reasoning Layer Evaluation (Trajectory Auditing)**:
   - Evaluates whether the agent selected the optimal sequence of tools.
   - Detects tool parameter misconfiguration, semantic drift, and infinite loops.
   - Leverages **OpenTelemetry traces** to capture full agent decision trajectories.

2. **Action Layer Evaluation (Outcome Verification)**:
   - Verifies whether the final side-effect in the target system was achieved accurately.
   - Employs deterministic tool mocking to isolate agent decisions from external environment flakiness.
