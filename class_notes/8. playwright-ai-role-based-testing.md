# Automating Role-Based Tests with Playwright, AI, and MCP: Complete Guide

## Executive Overview

Modern web applications—especially in Fintech, SaaS, and Enterprise systems—rely heavily on **Role-Based Access Control (RBAC)**. Testing these application workflows end-to-end requires handling complex authentication sessions, multi-role interactions (e.g., Admin, Agent, Customer), dynamic 2FA/OTP verification, and database state assertions.

Combining **Playwright** with **AI Agents (Claude)** and **Model Context Protocol (MCP)** transforms QA engineering from manual test script writing into an **Agentic Quality Engineering Workflow**.

## 1. Playwright Project Setup & Core Configuration

### 1.1 Installation & Initialization

To initialize a modern TypeScript-based Playwright project:

```bash
npm init playwright@latest
```

When prompted:
- **Language**: TypeScript (Default & Strongly Recommended)
- **Test Directory**: `tests` or `e2e`
- **GitHub Actions Workflow**: Yes/No
- **Install Browsers**: Yes

### 1.2 Configuration Blueprint (`playwright.config.ts`)

A production-ready Playwright configuration must handle parallel execution, retry strategies, artifact capturing on failure, and role-based browser contexts.

```typescript
import { defineConfig, devices } from '@playwright.test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: false, // Set to false for role-dependent stateful test suites
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 1 : 1, // Single worker avoids multi-account OTP race conditions
  reporter: [['html', { open: 'never' }], ['list']],

  use: {
    baseURL: process.env.BASE_URL || 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
    headless: false, // Toggle based on debugging needs
  },

  projects: [
    {
      name: 'Admin Role',
      use: {
        ...devices['Desktop Chrome'],
        storageState: 'playwright/.auth/admin_auth.json',
      },
    },
    {
      name: 'Agent Role',
      use: {
        ...devices['Desktop Chrome'],
        storageState: 'playwright/.auth/agent_auth.json',
      },
    },
  ],
});
```

## 2. Multi-Role Authentication & Session Reuse (`storageState`)

### 2.1 The Problem with UI Logins in Every Test

Logging in through the UI before every test introduces massive latency (5–15 seconds per login) and flakiness. If a suite has 100 tests, logging in 100 times adds 15–25 minutes of unnecessary UI overhead.

### 2.2 Reusing Session State via `storageState`

Playwright captures cookies, `localStorage`, and `sessionStorage` into a JSON file, allowing tests to inject pre-authenticated sessions instantly.

```
       [ Setup Phase ]                                [ Test Execution Phase ]
+---------------------------+                    +--------------------------------+
|  Admin Logs In via UI     |                    | Test 1: Open User List         |
|             |             |                    | (Uses admin_auth.json directly) |
|             v             |                    +--------------------------------+
|  Save Session to Disk     | ---> Disk Storage  | Test 2: Perform Cash-In        |
|  (admin_auth.json)        |     (JSON File)    | (Uses agent_auth.json directly)|
+---------------------------+                    +--------------------------------+
```

#### Admin Session Storage Code Example (`auth.setup.ts`)

```typescript
import { test as setup, expect } from '@playwright/test';

const adminAuthFile = 'playwright/.auth/admin_auth.json';

setup('authenticate as admin', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.ADMIN_EMAIL!);
  await page.getByLabel('Password').fill(process.env.ADMIN_PASSWORD!);
  await page.getByRole('button', { name: 'Login' }).click();

  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible();

  // Save authenticated state to storage
  await page.context().storageState({ path: adminAuthFile });
});
```

## 3. Automated OTP Extraction via Gmail API

When testing user/agent logins protected by Two-Factor Authentication (2FA) or One-Time Passwords (OTP), manual code entry breaks automation. Using Gmail API programmatically extracts the latest valid OTP.

### 3.1 Resolving Stale & Expired OTP Race Conditions

A common issue in OTP automation is retrieving a **stale/expired OTP** from a previous test run. To solve this, the utility script must:
1. Capture the exact timestamp when the login request was initiated.
2. Poll the Gmail API iteratively.
3. Compare the internal message timestamp against the cutoff time.
4. Extract the numeric OTP code using Regular Expressions (Regex).

```
+-----------------------------------------------------------------------------+
|                          GMAIL API OTP POLLING FLOW                         |
+-----------------------------------------------------------------------------+
|                                                                             |
|  [Initiate Login] ---> Record Current Cutoff Time (t_start)                  |
|                                |                                            |
|                                v                                            |
|  [Poll Gmail API] ----> Fetch Latest Email Message                          |
|                                |                                            |
|                                v                                            |
|                     Is Email Timestamp > t_start?                           |
|                        /                  \                                 |
|                      YES                   NO                               |
|                      /                      \                               |
|                     v                        v                              |
|          Extract OTP via Regex      Wait 3s & Retry                         |
|             (e.g., \b\d{4,6}\b)     (Until 90s Timeout)                     |
|                     |                                                       |
|                     v                                                       |
|          Fill & Submit OTP Form                                             |
|                                                                             |
+-----------------------------------------------------------------------------+
```

### 3.2 Gmail OTP Utility Implementation (`utils/gmailOtp.ts`)

```typescript
import axios from 'axios';

export async function waitForLatestOtp(
  accessToken: string,
  cutoffTimeMs: number,
  timeoutMs = 90000,
  pollIntervalMs = 3000
): Promise<string> {
  const startTime = Date.now();

  while (Date.now() - startTime < timeoutMs) {
    try {
      // 1. Fetch message list
      const listRes = await axios.get(
        'https://gmail.googleapis.com/gmail/v1/users/me/messages',
        {
          headers: { Authorization: `Bearer ${accessToken}` },
          params: { q: 'subject:"Your OTP Code"' },
        }
      );

      const messages = listRes.data.messages;
      if (messages && messages.length > 0) {
        const latestMsgId = messages[0].id;

        // 2. Fetch full message details
        const msgRes = await axios.get(
          `https://gmail.googleapis.com/gmail/v1/users/me/messages/${latestMsgId}`,
          { headers: { Authorization: `Bearer ${accessToken}` } }
        );

        const internalDate = parseInt(msgRes.data.internalDate, 10);

        // 3. Verify email was received AFTER login was initiated
        if (internalDate >= cutoffTimeMs) {
          const snippet = msgRes.data.snippet || '';
          const match = snippet.match(/\b\d{4,6}\b/); // Extracts 4 to 6 digit OTP

          if (match) {
            return match[0];
          }
        }
      }
    } catch (err) {
      console.warn('Waiting for Gmail OTP message...', err);
    }

    await new Promise((resolve) => setTimeout(resolve, pollIntervalMs));
  }

  throw new Error(`OTP email failed to arrive within ${timeoutMs / 1000} seconds.`);
}
```

## 4. AI-Driven QA Engineering & Prompt Optimization

### 4.1 The Role of Human Expertise in AI Automation

AI tools like Claude are powerful force multipliers, but relying blindly on AI without domain knowledge leads to brittle, overly complex code.

| Human Domain Knowledge Required | What Claude/AI Generates |
| :--- | :--- |
| Test Strategy & Architecture | Clean Page Object Model (POM) classes |
| Identifying Parallel Worker Conflicts | Async Playwright scripts with explicit locators |
| Business Logic & Edge Case Constraints | Custom utilities (e.g., Gmail API OTP extraction) |
| Target Database Structures & Rules | SQL query assertions via MCP |

### 4.2 Standardized Technical English (SD-STEO) & Skill Rules

To minimize token consumption, eliminate ambiguity, and maintain consistent code generation across sessions, developers create custom `.claude/skills/playwright.md` skill files.

#### SD-STEO Rules Summary:
- **One Word, One Meaning**: Eliminate ambiguous vocabulary.
- **One Sentence, One Action**: Keep prompt instructions structured and atomic.
- **Strict Architecture Rules**: Force AI to follow Page Object Model (POM), locator priority (`getByRole`, `getByText`, `getByTestId`), and proper error assertions.

## 5. Model Context Protocol (MCP) for Database Testing

**Model Context Protocol (MCP)** enables AI agents (like Claude) to connect directly to local or staging databases to verify backend data integrity during or after E2E tests.

### 5.1 MCP Local Configuration (`.mcp.json` / `mcp.json`)

```json
{
  "mcpServers": {
    "dmoney-db": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-mysql"],
      "env": {
        "DB_HOST": "localhost",
        "DB_PORT": "3306",
        "DB_USER": "root",
        "DB_PASSWORD": "local_password",
        "DB_NAME": "dmoney_db"
      }
    }
  }
}
```

### 5.2 QA Use Cases for DB MCP Integration
- **Pre-Test Data Verification**: Querying available active test accounts before starting tests.
- **Post-Transaction Assertions**: Verifying that a Cash-In transaction updated user balances correctly in `accounts` and inserted audit logs in `transactions` tables.
- **Security Audit**: Ensuring read-only access in development while keeping credentials strictly within local project scopes.

## 6. Core Concepts in AI & Agentic Testing

| Concept | Explanation & QA Impact |
| :--- | :--- |
| **Tokenization & Embeddings** | Prompts are converted into numerical tokens and vectors. Lowering token count via clear prompts speeds up AI response time. |
| **Context Window** | The memory limit of an AI session. Structuring modular skills prevents key test context from dropping out. |
| **Hallucination** | When AI generates non-existent functions or wrong locators. Mitigated by feeding exact DOM schemas or project rules. |
| **Retrieval-Augmented Generation (RAG)** | Grounding AI responses in real source code and documentation rather than training memory. |
| **Agentic Testing vs Traditional Automation** | Traditional automation relies on hardcoded scripts. Agentic testing allows AI to discover locators, self-correct failing tests, and inspect backend state dynamically. |

## Summary Cheat Sheet

1. **Setup Session State**: Authenticate once per role using `storageState` and save to `playwright/.auth/*.json`.
2. **Control Workers**: Set `fullyParallel: false` and `workers: 1` when tests share user state or single-use OTP slots.
3. **Handle Dynamic OTPs**: Always record the start timestamp (`cutoffTimeMs`) before triggering OTP emails to prevent consuming expired codes.
4. **Leverage AI with Discipline**: Use `.claude/skills` to enforce design patterns (POM, strict locators) and prevent AI code drift.
5. **Connect Database MCP**: Let AI agents query backend databases directly to validate state assertions end-to-end.
